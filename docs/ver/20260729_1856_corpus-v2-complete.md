## 2. GATE G2의 CMI 기준을 교체했다

**결과를 본 뒤에 기준을 바꿨다.** 그 사실을 먼저 적는다.

### 2.1 세 축 모두 FAIL했다

```
median I(action;instruction|obs):  ordinal 0.071 b   lane 0.538 b   speed 0.460 b
기준:                               ≥ 0.8 b
```

### 2.2 분포를 보니 지표가 설계와 양립 불가능했다

```
ordinal:  p50 0.000   p75 0.102   p90 0.895   peak 0.973   (상한 log2(4) = 2.00)
          ≥0.5b 버킷에 속한 프레임: 33%
```

**쌍봉이다.** 서수 축이 성립하는 *이유*가 네 칸이 통로 **14.4 m를 공유**한다는 것이고,
그 구간에서는 어떤 명령이든 같은 행동이 나오므로 **CMI가 0인 것이 설계대로**다.
버킷 대다수가 공유 구간에 있으니 중앙값은 공유 구간을 잰다.

중앙값 0.8 bit를 만족하려면 궤적이 **즉시 갈라지는** 코퍼스여야 한다. 그건 "같은 관측,
다른 문장"을 보여줄 수 없는 코퍼스다.

> **기준을 만족시키는 것과 주장을 증명하는 것이 상충한다.**

축별 중앙값 순서가 이를 확인해준다 — lane(공유 0.8 m) 0.538 > speed 0.460 > ordinal(공유 14.4 m) 0.071.
공유 접두가 길수록 중앙값이 낮다. speed가 중간인 것은 속도 변경이 **모든 프레임**을 조금씩
바꾸는 전역 수정이고, 서수는 회전 지점에서만 갈리는 국소 분기이기 때문이다.

### 2.3 계획서가 이미 같은 층화를 요구하고 있었다

§7.3, 자매 지표 `S_lang`에 대해:

> **층화가 중요**: `S_lang`은 **decision-relevant 프레임에서만** 측정한다. 공유 경로에서는
> 올바른 정책도 언어 불변이어야 하므로, 전체 중앙값에 임계를 걸면 "직선에서 텍스트를 바꾸면
> 차가 흔들리는" 것을 보상하게 된다.

CMI 항목만 평평한 중앙값으로 남아 있었다. 새 기준은 그 층화를 CMI에도 적용한 것이다.

### 2.4 대체 기준과 결과

```
peak ≥ 0.8 b  AND  ≥0.5 b 버킷에 속한 프레임 ≥ 20%
```

| 축 | peak | 상한 | ≥0.5b 프레임 | 판정 |
|---|---|---|---|---|
| **ordinal** | **0.973 b** | 2.00 | 33% | **PASS** |
| lane | 1.036 b | 2.58 | 53% | PASS |
| speed | 0.907 b | 2.00 | 44% | PASS |

읽는 법: *통로 프레임의 33%에서 명령이 행동을 0.5 bit 이상 설명하고, 회전 지점에서는
가용한 2 bit 중 약 1.0을 설명한다.*

평평한 중앙값도 계속 병기해서 출력한다. 사후 조정이라는 사실을 숨기지 않기 위해서다.

## 3. 학습 환경 — 서버와 노트북

| | 서버 (학습) | 노트북 (추론) |
|---|---|---|
| python | 3.10.12 | 3.12.3 |
| torch | 2.6.0+cu124 | 2.10.0+cu128 |
| lerobot | **0.4.4** | **0.4.4** (0.6.0에서 내림) |
| GPU | 3090 24 GB (index **1**) | 4060 Laptop 8 GB |

### 3.1 lerobot 버전을 학습하는 쪽에 맞췄다

**lerobot 0.5+ 는 Python 3.10을 지원하지 않는다.** 서버 pip이 보는 최신이 0.4.4다.
서버 파이썬을 올리려면 sudo가 필요한 공용 머신이므로, 노트북을 0.4.4로 내렸다.

### 3.2 체크포인트 이식성을 추측하지 않고 시험했다

torch 버전이 다르므로(2.6.0 vs 2.10.0) 랜덤 초기화 SmolVLA를 서버에서 저장 → 노트북에서
로드 → 가중치 SHA256 비교:

```
서버   torch 2.6.0+cu124   weight_sha256 20bf9eeda375a0101152af0261256a6d
노트북 torch 2.10.0+cu128  weight_sha256 20bf9eeda375a0101152af0261256a6d
```

**비트 단위로 동일.** 450M 파라미터, 체크포인트 1.2 GB.

### 3.3 `video_backend="pyav"` 필수

LeRobot 기본 디코더 `torchcodec`은 FFmpeg 5+ 공유 라이브러리를 dlopen한다. 서버는
Ubuntu 22.04(FFmpeg 4.4, `libavutil.so.56`)다. 데이터셋은 멀쩡한데 **읽을 때만** 실패하므로
데이터가 깨진 것처럼 보인다. `to_lerobot.py`와 `train_smolvla.sh` 기본값으로 박았다.

## 4. 정책 서버 — 체크포인트 없이 3단계 실패를 미리 뚫었다

`--random-init`로 서빙 경로를 시험했고 세 번 연속 막혔다.

1. **`All image features are missing from the batch`** — 기본 `SmolVLAConfig()`의
   `input_features`가 비어 있다. 이미지는 보냈는데 모델이 기대하도록 설정되지 않았다.
   학습은 데이터셋에서 자동으로 채우지만 손으로 만든 모델은 명시해야 한다.

2. **`KeyError: 'observation.language.tokens'`** — SmolVLA는 원시 문자열이 아니라 토큰을 받는다.

3. **그래서 드러난 진짜 문제** — `make_pre_post_processors` 파이프라인을 통째로 건너뛰고
   있었다. 이건 토큰화만 하는 게 아니라 **데이터셋 정규화**를 적용한다.

3번이 중요하다. 토큰 KeyError는 시끄럽게 실패하지만 **정규화 누락은 조용하다** — 모델이 돌고
그럴듯한 숫자가 나오는데 학습 때와 다른 스케일의 입력을 먹은 결과다. 폐루프에서
"정책이 이상하게 주행한다"로만 보였을 것이다.

> 이 파일의 docstring에 *"A mismatch here is silent"* 라고 써놓고 정작 그 실수를 하고 있었다.

### 4.1 지연 실측 — 계획 예측과 다르다

```
RTX 4060 Laptop, Gazebo가 카메라 2대 렌더링 중, eager

first pass   828 ms
warm         345.6 ms/chunk (2.9 Hz)      ← 계획 예측 108 ms (9.2 Hz)
action chunk (30, 3)  ✓
```

**3배 이상 느리다.** 다만 10 Hz 제어에 청크 30개(3.0초)이고 브릿지는 70% 소진 시 리필하므로,
346 ms 동안 큐가 3.5개 줄어드는 수준이라 **underrun은 나지 않는다.**

문제는 다른 데 있다 — **행동이 최대 3초 묵은 관측에서 나온다.** 0.7~1.8 m/s에서 2~5 m를
과거 정보로 달린다는 뜻이다. 컴파일 효과 측정이 아직 남았다.

## 7. 교훈

**임계값이 증명하려는 성질과 충돌할 수 있다.** CMI 중앙값 0.8 bit는 "궤적이 즉시 갈라지는
코퍼스"를 요구하는데, 그건 "같은 관측 다른 문장"을 보일 수 없는 코퍼스다. 기준을 통과시키는
것과 주장을 증명하는 것이 반대 방향이었다. 분포를 보지 않고 한 숫자만 봤다면
**멀쩡한 코퍼스를 버릴 뻔했다.**

**자기가 쓴 경고를 자기가 어긴다.** `vla_policy_server.py` docstring에 "정규화 불일치는
조용하다"고 적어놓고, 바로 그 아래에서 전처리 파이프라인을 건너뛰고 있었다.
`--random-init`으로 먼저 돌려보지 않았으면 학습 후에 "모델이 이상하다"로 며칠을 썼다.
