## 1. 그룹이 수집 단위다 — 에피소드가 아니라

**반사실 그룹** = 하나의 시작 pose + 여러 명령. 그룹 안의 모든 에피소드는 **같은 pose로 리셋**되므로,
그룹 내부의 궤적 차이는 문장 말고는 설명할 게 없다.

```
p0017  axis=ordinal  start (-10.79, -22.36, -11.7°)
   v0  bay4  @1.8  "Go park in the 4th slot, briskly."
   v1  bay1  @1.8  "Go park in the 1st slot, briskly."
   v2  bay3  @1.8  "Enter the 3rd parking bay, at a fast speed."
   v3  bay2  @1.8  "Enter the second parking bay, at a fast speed."
```

### 1.1 그룹은 축을 정확히 하나만 바꾼다

처음에는 칸 4 × 속도 3을 한 그룹 안에서 교차시키려 했다. **틀렸다.** 그러면 bay1@slow 대
bay4@fast 쌍이 두 가지 이유로 갈라지고, **하나의 발산 수치를 두 원인으로 되돌리는 방법은 없다.**

그래서 `cf_axis`를 그룹에 붙였다.

| 축 | 그룹 구성 | 무엇의 증거인가 |
|---|---|---|
| `ordinal` | 4칸, 속도 고정 | **관측으로 복원 불가능한 축.** 기준 (a)의 핵심 |
| `speed` | 1칸, 속도 3단 | 스케줄 축. 형상은 바닥에 머물러야 함 |
| `lane` | 목표 1개, 차선 2개 | 형상 축 |
| `floor` | **같은 요청 2회** | 이 세션의 노이즈 바닥 |

속도는 ordinal 그룹 **사이에서** 순환하므로, 축을 오염시키지 않으면서 라벨로서는 균형을 유지한다.

### 1.2 floor 그룹을 넣은 이유

모든 비율의 분모가 **9.5 cm**였다. 그 값은 GATE G1 — 목표 없이 자유주행시킨 물리 노이즈를
다른 날 잰 것이다. 수집 조건에서 다시 재지 않으면 분모가 계속 가정으로 남는다.

floor 그룹의 두 변형은 템플릿을 독립적으로 뽑으므로 보통 **같은 요청의 다른 표현**이 된다.
오라클에게는 아무 차이가 없다 — 오라클은 문장을 보지 않고 `oracle_goal`만 받는다. 따라서
측정되는 것은 순수한 물리 산포다. **같은 쌍이 정책 주행 시점에는 패러프레이즈 불변성 시험이 된다.**

## 2. 시작점을 흩뿌린다

모든 에피소드가 동일한 pose에서 출발하면 **"4.2초 뒤에 우회전"이 학습셋에서 완벽한 정책**이 되고
그 바깥에서는 쓸모가 없다.

```python
connector_starts(..., index_lo=0.0, index_hi=0.6)   # 커넥터 앞 60% 구간
lat_jitter  = 0.6 m      # 진행방향 수직 오프셋
yaw_jitter  = 6°
```

`index_hi=0.6`은 **공유 통로 전체가 모든 에피소드 안에 남도록** 자른다. 서수 축이 공유 접두에
걸려 있으므로, 그 뒤에서 출발하면 재려는 대상 자체가 줄어든다.

횡 오프셋에는 두 번째 목적이 있다. **pure pursuit 시범자는 원래 복구 동작을 보여주지 않는다** —
경로 위에서 출발해 경로 위에 머물기 때문이다. 오프셋 출발은 오라클이 되돌아오도록 강제하고,
그 프레임이 코퍼스에서 유일한 보정 사례다.

**시작점을 링 위로 15 m 더 물리는 것은 아직 안 된다.** 주차 경로가 커넥터에서 시작하므로 그
바깥의 pose는 경로상 최근접점이 없고, pure pursuit이 커넥터 입구로 직행한다. 링 목표 →
주차 목표 전환이 필요하고 아직 없다.

## 3. 타임아웃을 거리에서 계산한다

고정 타임아웃은 bay1@fast에는 헐겁고 bay4@slow에는 단두대다. 그리고 **잘린 주행은 코퍼스에
`timeout`으로 들어가 제어 실패처럼 읽힌다** — 실제로는 그런 적이 없는데.

```
timeout = 경로길이 / 속도 × 2.5 + 20 s
```

bay1@fast 58 s, bay4@slow 157 s로 자동으로 벌어진다.

링 목표도 같은 이유로 범위를 강제한다. 루프가 일방통행이라 **2 m 뒤에 있는 목표는 140 m 앞에
있는 목표다.** 제한 없이 고르면 3초짜리 에피소드 아니면 4분짜리 랩이 나온다.

```python
RING_GAP_MIN_M, RING_GAP_MAX_M = 22.0, 55.0     # 양쪽 차선 모두에서 만족해야 함
```

조건을 만족하는 waypoint가 없는 그룹은 **버리고 몇 개 버렸는지 출력한다.** 조용히 줄이면
커버리지를 다 채운 것처럼 읽힌다.

## 4. 실패를 기록한다

`termination`이 6값인 이유가 여기 있다. 타임아웃된 에피소드는 성공한 에피소드가 아니고,
5%가 타임아웃되는 세션은 0%인 세션과 **다른 데이터셋**이다.

- 리셋은 최대 3회 재시도한다. 그룹 안의 변형이 서로 다른 pose에서 출발하면 그 그룹은
  **쌍을 하나도 만들지 못하므로**, 리셋에 시간을 더 쓸 가치가 있다.
- 결과는 `manifest.jsonl`에 계획과 나란히 쌓인다. 중간에 죽여도 해석 가능하다.
- **완성된 그룹 수를 에피소드 수와 따로 센다.** 변형 하나가 빠진 그룹은 그 비교에 대해
  쌍을 기여하지 않는다.

## 5. 명령 뱅크 — 학습 전에 커밋되어야 한다

A3 절제는 "정책이 언어를 따르는가, 아니면 문자열 몇 개를 외웠는가"를 묻는다.
**heldout 표현이 모델이 학습셋을 보기 전에 고정되어 있어야만** 답할 수 있는 질문이다.
결과를 본 뒤에 표현을 추가하면 시험이 조용히 학습셋으로 바뀐다.

분할은 **표면형에 대해서만** 한다. bay3은 양쪽 분할에 모두 나온다 — 그렇지 않으면 heldout
실패가 "표현을 못 알아들었다"인지 "본 적 없는 목표다"인지 구분되지 않는다.

| | train | heldout |
|---|---|---|
| `park_bay` 템플릿 | 8 | 4 |
| `ring_goal` 템플릿 | 8 | 4 |
| 서수 어휘 | first / 1st … | number one / nearest … |

### 5.1 말하지 않은 것은 명령할 수 없다

속도가 에피소드마다 달라지는데 문장에 안 나오면, **같은 문장이 여러 궤적에 대응하고 정책은
그 평균만 배울 수 있다.** 그래서 `speed_clause`는 선택이 아니라 모든 템플릿에 붙는다.

```
"Park in the second bay on the right, slowly."
                                      ^^^^^^ 생략 불가
```

### 5.2 "왼쪽 차선"이 lane1이 맞는지 확인했다

어휘가 틀리면 정책은 **잘못된 대응을 정확하게** 학습한다. 실측:

```
진행방향 기준 lane1이 왼쪽인 샘플: 41/41
루프 방향: 반시계 (signed area +1301.7)
```

lane1 = 안쪽 = 왼쪽. 어휘 통과.

### 5.3 "첫 번째 칸"의 기준

차는 통로를 +y로 진입하고 4칸이 모두 오른쪽에 있다. bay1(y=−9.355)이 **가장 먼저 만나는 칸**이다.
서수는 지도 인덱스가 아니라 **주행 순서**로 정의된다. `zone_map.yaml`의 Slot1–4와 y 순서가
일치하고 오차 6 cm 이내다.

## 6. 실기동에서 잡은 버그 2건

두 건 다 **드라이버는 100% 성공을 보고했고**, 데이터는 손상되어 있었다.

### 6.1 recorder 2개가 한 세션에 기록했다

`kill $(cat pid)`가 `ros2 run` 래퍼만 죽여서 노드가 살아남았다. 둘 다 `/recorder/command`를
구독하므로 모든 start에 반응하고, 둘 다 `len(os.listdir(...))`로 인덱스를 고르므로 **동시 start에는
같은 번호를 받는다.** 그리고 하나의 `frames.jsonl`에 번갈아 쓴다.

결과물은 건강해 보인다 — meta.json이 있고, 프레임 수도 그럴듯하고, 아무 에러도 없다.
디렉터리가 6개 요청에 10개 생긴 것으로만 드러났다.

```python
# 세션 디렉터리에 flock. 조언적이고 fd 단위라 프로세스가 어떻게 죽든 자동 해제된다.
fcntl.flock(self._lock_fd, fcntl.LOCK_EX | fcntl.LOCK_NB)
```

에피소드 디렉터리도 `exist_ok=False` 후 번호 증가로 바꿨다. `exist_ok=True`는 두 번째 호출이
첫 번째 에피소드를 **제자리에서 덮어쓰게** 한다.

### 6.2 에피소드 절반에서 tf pose 스트림이 완전히 죽어 있었다

이게 더 나쁘다.

```
ep_0000  tf= 1493 (24.4 Hz)   ep_0001  tf= 0 (0.0 Hz)
ep_0002  tf= 1309 (20.1 Hz)   ep_0003  tf= 0 (0.0 Hz)
ep_0004  tf= 1971 (28.5 Hz)   ep_0005  tf= 0 (0.0 Hz)
```

**정확히 하나 걸러 하나.** 그리고 10개 전부 `valid: true`였다.

원인 사슬:

1. `_last_tf_xy`가 에피소드 경계를 넘어 살아남는다
2. 다음 에피소드에서 차는 리셋으로 **텔레포트**되어 있다
3. `_tf_cb`가 그 변위를 "엔티티 순서가 바뀌었다"로 해석하고 `_ego_idx = None`
4. 재식별은 **다음 `start_episode`에서만** 일어난다 → 이번 에피소드 내내 tf가 없다
5. CLI 폴백(15 Hz)이 계속 쓰이므로 `n_poses` 총합은 그럴듯하다

**SE(2) 행동 라벨은 tf에서 나온다.** 절반의 에피소드가 15 Hz CLI 스트림만 가진 채 학습에
들어갈 뻔했다.

수정 3가지:

```python
# 1. 에피소드 간 텔레포트는 이상이 아니다
start_episode:  self._last_tf_xy = None

# 2. 재식별을 전용 스레드로 — 58 Hz 콜백 안에서 subprocess를 3초 기다릴 수 없다
threading.Thread(target=self._reident_loop, daemon=True)

# 3. 구멍을 메타데이터에 드러낸다
meta["n_poses_tf"], meta["n_poses_cli"]
if n_tf / dur < 5.0:  valid = False
```

## 7. `verify_corpus.py` — 이 문서의 진짜 결론

위 두 건은 **수집 드라이버가 100% 성공을 보고하는 동안** 일어났다. 드라이버는 자기가 요청한
일이 끝났는지만 안다. 코퍼스가 **무엇을 위한 것인지**는 검사하지 않는다.

그래서 세션을 디스크에서 다시 읽어 검사하는 게이트를 만들었다. 실패하면 종료코드가 0이 아니다.

| 게이트 | 검사 |
|---|---|
| G-I 무결성 | meta.json 존재, 스트림 비어있지 않음, 타임스탬프 단조증가·중복 없음, **tf 스트림 ≥ 5 Hz**, 프레임 행 수 = 파일 수 |
| G-R 레이트 | 프레임 30 Hz ±15%, 드롭 0 |
| G-C 반사실 | 그룹 내 시작 pose 동일, **축별로 따로** 발산 보고, 바닥 대비 배율 |
| G-L 언어 | 고유 문장 수, 템플릿 커버리지, 목표 빈도 균형 |

### 7.1 축을 라벨이 아니라 데이터에서 판정한다

`pair_axis()`는 그룹이 선언한 `cf_axis`를 믿지 않고 **기록된 슬롯에서 무엇이 실제로 다른지**를
다시 계산한 뒤 선언값과 대조한다. 두 가지를 동시에 바꾸는 계획 버그는 라벨로 덮이지 않고
데이터에서 잡힌다.

### 7.2 실측 — 15 에피소드 스모크 (5그룹, 4축, 12.6분)

```
G-I 무결성   PASS  15개, 스트림 정상, tf 26~29 Hz
G-R 레이트   PASS  프레임 중앙값 28.06 Hz, 드롭 0
G-C 반사실   PASS
G-L 언어           14/15 고유 문장
```

| 축 | n | D_shape 중앙 | 소요시간 비 | **공유 접두** | 바닥 대비 |
|---|---|---|---|---|---|
| `ordinal` | 12 | **6.407 m** | 1.13× | **16.8 m** | **26.6×** |
| `lane` | 1 | 4.635 m | 1.08× | 1.2 m | 26.7× |
| `speed` | 3 | 0.273 m | **1.67×** | 22.0 m | 1.4× (직교, 정상) |
| `floor` | 1 | 0.174 m | 1.00× | 21.6 m | 1.0× |

공유 접두 16.8 m가 경로 설계값 **16.12 m**와 일치한다 — 커넥터 13.32 + 통로 3.02.
그 16.8 m 동안 카메라가 보는 장면은 동일하고 다른 것은 문장뿐이다.

### 7.3 지표를 두 번 고쳤다 (둘 다 데이터가 아니라 지표가 틀렸다)

**(a) 공유 접두가 1.7 m로 나왔다.** 설계값 16.12 m의 10분의 1이다. 원인을 파보니:

```
idx 40:  A=(-4.96,-18.34)   B=(-4.91,-18.09)   |A-B| = 0.251 m
```

두 주행은 **같은 선 위에 있고 B가 0.25 m 앞서 있을 뿐**이다. 리스트 인덱스로 짝지으면
"A의 40번째 기록점"과 "B의 40번째 기록점"을 비교하게 되고, 속도가 완전히 같지 않으면
**종방향 위상차가 경로 이탈로 읽힌다.**

호길이로 리샘플해서 "같은 거리를 달린 뒤 같은 위치인가"를 묻도록 고쳤다. 1.7 m → **16.8 m**.

**(b) 속도 쌍의 `D_sched`가 0.165 m로 나왔다.** 속도가 스케줄 축이라는 주장의 근거인데
사실상 0이다. 원인:

`D_sched`는 호길이 차이인데, 주차 에피소드는 **양쪽 다 같은 칸까지 같은 경로를 완주한다.**
호길이가 같은 게 당연하다. [18:21 문서](20260728_1821_route-oracle.md)의 12.68 m는 **고정
14초 창**에서 나온 값이고 — 빠른 쪽이 더 멀리 갔을 뿐이다 — 목표에서 종료되는 에피소드에는
그 구도가 존재하지 않는다.

목표 종료 에피소드의 스케줄 지표는 **소요 시간**이다. 같은 데이터로 다시 재니 **1.67배**
(느림 54 s / 빠름 22.5 s). 축은 살아 있었고 자를 잘못 댔던 것이다.

### 7.4 속도 축은 반대 방향으로 검사한다

속도 쌍은 **형상을 바꾸면 안 된다.** 직교성이 곧 주장이기 때문이다. 형상 게이트에 함께 넣으면
코퍼스가 옳다는 이유로 실패한다.

```python
shape_axes = {"ordinal", "lane", "goal", "mixed"}   # D_shape가 커야 통과
speed:  worst D_shape <= 0.6 m                      # 작아야 통과
```

## 8. 미해결

1. **링 → 주차 전환.** 주차 에피소드는 여전히 커넥터 위에서 시작한다. "T2까지 갔다가 2번 칸에
   대"가 하나의 에피소드로 이어지려면 목표 전환이 필요하다.
2. **B그룹 주차칸 미사용.** 사방이 막힌 사각형.
3. **`off_track` 판정이 오라클의 이탈 중단에 의존한다.** 충돌 지오메트리가 없어 물리적
   이탈 판정이 없다.
4. **heldout 평가 코퍼스 미수집.** `--split heldout`은 구현됐지만 실행 안 함.
5. **20회 중 1회 G1 실패 원인 미규명.** 이제 `manifest.jsonl`의 `reset_ok`/`reset_detail`에
   남으므로 재발하면 근거가 쌓인다.

## 9. 교훈

**"성공적으로 완료됨"은 데이터에 대한 진술이 아니다.** 두 버그 모두 드라이버가 100%
성공을 보고하는 동안 일어났고, 둘 다 조용히 손상시켰다. 완료를 보고하는 코드와 결과물을
검사하는 코드는 **다른 코드여야 한다.**

**폴백은 실패를 숨긴다.** CLI pose 폴백이 없었다면 tf 스트림이 죽은 순간 `poses.jsonl`이 비어
즉시 드러났을 것이다. 폴백이 있으니 총합이 그럴듯해져서 절반의 코퍼스가 통과할 뻔했다.
폴백을 쓸 때는 **폴백이 쓰였다는 사실 자체를 기록해야 한다** — 지금은 `n_poses_tf` /
`n_poses_cli`로 분리한다.

**축을 하나씩만 바꿀 것.** 두 개를 동시에 바꾼 쌍의 발산 수치는 사후에 분해할 수 없다.

**지표가 이상하면 대상이 아니라 지표를 의심할 것.** 이번에 두 번 나왔다 — 공유 접두 1.7 m와
속도 `D_sched` 0.165 m. 둘 다 데이터는 정상이었고 자가 틀렸다. 그대로 뒀다면 "서수 축의 공유
구간이 짧다"와 "속도는 스케줄을 안 바꾼다"는 **정반대의 결론**을 코퍼스 설계에 반영했을 것이다.
[18:21 문서](20260728_1821_route-oracle.md) §8에 같은 교훈이 이미 있었다.

## 10. 카메라 — 새 센서 추가 (`/vla_camera/image_raw`)

수집 직전에 확인한 사항이다. 통로에서 **회전을 시작하는 순간 목표 칸이 프레임 밖에 있다.**

```
hfov 62.2°  (반각 31°)         카메라 높이 2.05 m, 피치 5.7° 하향
회전 시작점에서 목표 칸 중심: 앞 5.23 m, 우 5.23 m = 축에서 45°   → 프레임 밖
우측 5.23 m 지점이 프레임에 들어오려면 앞으로 8.67 m 이상 떨어져 있어야 함
프레임의 46%가 특징 없는 하늘
```

실제 프레임(`ep_0000/frames/000683.jpg`, 회전 시작점)에서 확인: 왼쪽의 B그룹 칸은 선명하게
보이지만 **오른쪽 목표 칸은 보이지 않는다.** B그룹은 간격 5.63 m, A그룹은 3.63 m라
왼쪽 칸을 세어 오른쪽을 추정할 수도 없다.

이것이 기준 (a)에 직접 걸린다 — 정책이 결정 시점에 목표를 못 보면, 남는 것은
"N미터 뒤에 우회전"을 외우는 것뿐이고 그건 언어의 시각적 접지가 아니다.

### 10.1 기존 카메라를 고치지 않고 하나 더 달았다

`prius_cam`은 그대로 둔다. YOLO 차선 파이프라인(`track_rois.json`, `lane_info_extractor`)이
그 화각에 맞춰 보정돼 있고, 619 에피소드 구 코퍼스도 그 카메라로 찍혔다. 둘 다 유효하게 유지된다.

```
/camera/image_raw       narrow, 62.2°   — YOLO 파이프라인, 구 코퍼스
/vla_camera/image_raw   wide,  100°     — VLA 수집          ← 신규
```

### 10.2 화각만 넓히면 각도 문제가 위치 문제로 바뀐다

먼저 지붕의 카메라를 그대로 두고 화각만 넓히고 아래로 기울였다. **하늘 46%가 보닛·실내
50%로 바뀌었을 뿐이다.** 죽은 영역을 더 큰 죽은 영역과 맞바꿨다.

수평 화각을 넓히면 **수직 화각도 같이 넓어진다**(83.6°). 카메라가 지붕에 있는 한, 하늘을
자를 만큼 기울이면 반드시 자기 보닛이 들어온다. 각도로 풀 수 없는 문제다.

센서를 **자기 축을 따라 앞으로 2.6 m** 옮겨 앞 범퍼에 놓았다(모델의 코가 y=−2.24). 거기엔
볼 차체가 없다.

| | 정보를 담은 프레임 비율 |
|---|---|
| narrow, 지붕 | **52%** (하늘 48%) |
| wide, 범퍼 | **71%** (하늘 29%, 차체 0%) |

### 10.3 진짜 단서는 목표 칸이 아니라 "남은 칸 수"였다

100°로 넓혀도 목표 칸은 프레임 **맨 오른쪽 가장자리**에 겨우 걸린다. 실제로 쓸 수 있는 단서는
따로 있었다 — 회전 시작 시점에 **앞쪽에 남아 있는 칸 개수**다.

bay2 회전 시작점 기준:

| | 축에서 각도 | 62° 렌즈 | 100° 렌즈 |
|---|---|---|---|
| bay2 입구 (목표) | 45° | ✕ | 가장자리 |
| bay3 입구 | 30.6° | 경계 | ✓ |
| bay4 입구 | 22.7° | ✓ | ✓ |

**"앞에 두 칸 남았으면 지금 돈다"는 단일 프레임 단서다.** 지나간 칸을 세는 것은 아니다.
62° 렌즈에서는 bay3가 31° 반각 경계에 걸려 이 단서가 성립하지 않았다.

B그룹(왼쪽) 칸으로 대신 셀 수도 없다 — 간격이 5.63 m 대 3.63 m로 다르다.
