## 2. 실패 1 — 시계가 멈춰 있었다

첫 실기동 기록의 실태:

```
frames   n= 322  unique_t= 322  30.30 Hz     <- 정상
poses    n= 509  unique_t=   1  span 0.000s  <- 전부 t=0.0
control  n= 141  unique_t=   1  span 0.000s  <- 전부 t=0.0
```

`use_sim_time:=true`인데 **`/clock`을 발행하는 주체가 없었다.** 노드 시계는 `/clock`을 기다리며
0에 고정되고, `get_clock().now()`가 영원히 0을 돌려준다.

프레임만 멀쩡했던 이유는 이미지 `header.stamp`(시뮬레이터가 직접 채움)를 쓰기 때문이다.
**전면 실패가 부분 성공처럼 보인 원인**이 정확히 이것이다.

`driving_sim.launch.py`에 `/clock` 브리지 추가 → 실측 **1000 Hz**.

### 그리고 이건 레코더가 막았어야 할 실패였다

`_check_clock()`이 `use_sim_time` **파라미터 값만** 확인하고 시계가 실제로 진행하는지는
보지 않았다. 조용한 실패를 막겠다고 만든 물건이 조용히 실패했다.

→ `clock_alive()` 추가. 시계가 안 돌면 **기록을 거부한다**(경고가 아니라 거부).
→ 리샘플러에도 gate 0 추가: 타임스탬프가 전부 동일하면 정확한 진단과 함께 거부.

## 3. 실패 2 — 콜백이 락을 쥔 채 디스크에 썼다

계측 결과:

```
recording: q=120/600 wrote=49 enc=15.02ms io=29.77ms busy=2.15s / 2s heartbeat
```

writer 스레드가 **90% 포화**. 단독 벤치는 인코딩+쓰기 2.12 ms(472 Hz 상한)인데
실부하에서 45 ms로 늘었다.

원인 두 개:
1. **`JsonlWriter`가 줄마다 flush.** 초당 ~110회 syscall.
2. **pose 콜백(58 Hz)과 control 콜백이 공유 락을 쥔 채 디스크에 flush.**
   writer 스레드가 락을 얻지 못했다.

구 레코더의 "콜백 안에서 디스크 I/O"를 비판해 놓고 다른 형태로 반복한 셈이다.

수정:
- `JsonlWriter`에 자체 락 + 64줄마다 flush + 64 KB 버퍼
- 모든 콜백이 **락 밖에서** 쓰도록 변경(락은 에피소드 상태 교체에만)
- **writer 스레드 3개.** `cv2.imencode`가 GIL을 놓으므로 실제로 병렬화된다

결과: 큐가 `120→152→186`(계속 증가)에서 **줄곧 `0/600`** 으로.

## 4. 실패 3 — pose 소스 교체

`WorldPoseStream`은 `gz topic -e` 서브프로세스의 텍스트를 파이썬으로 파싱한다.
실측 25 Hz에 **562 ms 구멍**. SE(2) 라벨을 미분해 낼 스트림으로는 너무 거칠다.

네이티브 브리지(`dynamic_pose/info` → `TFMessage`)로 교체: **58.8 Hz, 지터 0.14 ms.**
브리지가 엔티티 이름을 잃어버리므로(`frame_id` 비어 있음) `gz model -p` 값과 위치를 대조해
인덱스를 1회 식별한다. 차량 정지 시 **오차 0.0~4.5 cm, 차순위 엔티티는 20.7 m 밖** — 명확하다.

## 5. 게이트 재설계 — 프록시가 아니라 실제 오차로

거부 사유가 계속 바뀌길래 임계값을 낮추는 대신 **판정 기준 자체를 물리량으로** 바꿨다.

| 이전 | 문제 | 이후 |
|---|---|---|
| `소스 프레임 구멍 > 0.20s` | 15초 에피소드의 231 ms 딸꾹질 하나가 격자점의 ~1%에만 영향을 주는데 에피소드 전체를 버림. 게다가 **격자점별 최근접 오차**가 이미 5% 예산으로 같은 것을 더 정확히 잰다 | `> 0.50s` (스트림이 깨진 경우만) |
| `pose 보간 구간 > 0.10s` → `0.25s` | 구간 길이는 프록시다. 직진 중 긴 구간은 무해하고, 선회 중 짧은 구간은 유해하다 | **보간 오차 자체**로 판정: 현-호 sagitta = \|ω\|·v·dt²/8, 임계 **2 cm** |

2 cm는 G1에서 측정한 **9.5 cm 리셋 노이즈 바닥**보다 한참 아래라, 통과한 에피소드의 라벨이
보간 오차에 지배될 수 없다.

효과: 353 ms 구멍이 있던 실기동 에피소드가 **실제 오차 0.48 cm**로 계산되어 정당하게 통과했다.
구간 기준이었다면 좋은 데이터를 버렸을 것이다.

## 7. pose 소스 프레임 검증

행동 라벨은 ego 프레임 SE(2) 델타이므로 **프레임이 틀리면 코퍼스 전체가 회전한다.**
그리고 데이터는 완벽히 자기일관적으로 보이므로 하류에서 검출할 방법이 없다.

### 측정한 것

`calibrate_yaw_offset.py`를 만들어 **직진 주행**으로 순수 프레임 오프셋을 쟀다
(선회하면 사이드슬립이 섞이므로 직진이어야 한다). 시작 방향 4개(−90/0/+90/180°) 전부:

```
gz model -p (모델 원점) : -90.00 deg   sd 0.00 deg   n=28
```

**정확히 −90°, 편차 0.** `policy_node.py`의 `direct_yaw_offset = -π/2`와 일치한다.

### 문제로 보였던 것

선회 중 두 소스가 갈리는 것처럼 보였다: 모델 원점 −79.5°(슬립 10.5°) vs TF −67.5°(슬립 22.5°).

## 7.1 해소 — 오진이었다

강체는 모든 점이 하나의 순간회전중심(ICR)을 공유한다. 정상상태 원 주행(v=1.2, ω=0.30 명령)을
14초 기록해 두 궤적에 각각 원을 적합했다:

| | CLI (모델 원점) | TF (dynamic_pose[0]) |
|---|---|---|
| 원 중심 | (5.118, 20.551) | (5.117, 20.551) |
| 반지름 | 4.293 m | 4.293 m |
| 적합 잔차 | 5.8 mm | 5.8 mm |
| 슬립각 | +20.04° | +20.19° |

**ICR 간격 0.0 cm, 반지름 차이 0.0 cm — 두 소스는 같은 점을 보고 있다.**
`v/ω = 4.260 m` vs 적합 반지름 `4.293 m`로 **3.4 cm 일치**, 강체 운동학이 성립한다.

### 앞선 불일치의 원인

`query_world_pose`는 `gz model -p` **서브프로세스**를 부르며 실부하에서 ~600 ms 걸린다.
그 사이에 차가 움직이므로, CLI 값과 TF 값을 짝지어 비교하면 **호출 지연만큼 어긋난 두 시점**을
비교하게 된다. 앞서 측정한 0.345 m 오프셋과 12° 각도 차이가 전부 여기서 나왔다.

→ 비교에는 `WorldPoseStream`(백그라운드 스레드)을 써야 한다. 레코더는 이미 그렇게 하고 있다.

### 사이드슬립은 오차가 아니라 실제 거동

`|dy|/dx = 0.41`을 "물리적으로 불가능"이라고 판단했던 것도 틀렸다.
슬립각 20.04°를 자전거 모델로 역산하면:

```
tan(beta) = d*w/v  ->  d = v*tan(beta)/w = 1.554 m
시뮬 휠베이스 2.86 m -> 휠베이스의 54% 지점
```

후륜축=0%, 전륜축=100%인 자전거 모델에서 **54%는 차량 중앙**이다. 모델 원점이 있어야 할 자리다.
즉 ego-frame의 `dy`는 이 차량 모델의 **실제 사이드슬립**이고, 정책이 학습해야 할 거동이다.

### 확정 사항

- **프레임 오프셋 = −90.00°** (직진 4방향, sd 0.00). `policy_node.py`의 `direct_yaw_offset`과 일치
- 두 pose 소스 모두 사용 가능. 레이트가 높은 TF 브리지를 기본으로 하고, CLI는 교차검증용으로 병기
- `--yaw-offset-deg`는 필수 인자로 유지한다. 값이 확정됐어도 **묵시적 상수로 두지 않는다**

## 9. 교훈

**합성 테스트는 계산을 검증하지 시스템을 검증하지 않는다.** 리샘플러의 SE(2) 수학은 합성
데이터에서 오차 0.005%로 맞았다. 실기동에서 드러난 다섯 가지 — 없는 시계, 락 경합, writer
포화, QoS 깊이, 프레임 오프셋 — 중 어느 것도 합성 테스트로는 잡히지 않는다.

**게이트가 계속 걸리면 임계값이 아니라 판정 기준을 의심해야 한다.** 세 번 완화한 뒤에야
"구간 길이"가 프록시이고 "보간 오차"가 실체라는 걸 알았다. 임계값을 계속 낮췄다면 게이트를
무의미하게 만들었을 것이다.
